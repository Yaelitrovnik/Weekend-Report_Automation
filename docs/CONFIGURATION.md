# Weekend Report Configuration

**Documentation synchronized:** 2026-09-16

## 1. Configuration Model

Weekend Report uses a strict separation between application code, deployment configuration, and business policy.

```text
Docker image
  -> application code and runtime scripts

deploy/docker/.env
deploy/docker/env/*.env
  -> environment-specific runtime values and secrets

deploy/docker/config/rules.yml
  -> version-controlled business and validation policy
```

The application does not use per-module deployment YAML for site inventory, server inventory,
expected services, or Splunk dashboard definitions.

There is one runtime policy source:

```text
deploy/docker/config/rules.yml
```

Production Compose mounts it read-only as:

```text
/app/config/rules.yml
```

Runtime secrets and deployment-specific values must not be baked into the image.

## 2. Deployment Files

The checked-in templates are:

```text
deploy/docker/.env.example

deploy/docker/env/
  app.env.example
  portainer.env.example
  doctor.env.example
  rabbitmq.env.example
  recording.env.example
  infrastructure.env.example
  splunk.env.example
```

On the deployment/build PC, create the real non-committed files:

```text
deploy/docker/.env

deploy/docker/env/
  app.env
  portainer.env
  doctor.env
  rabbitmq.env
  recording.env
  infrastructure.env
  splunk.env
```

The real files are intentionally ignored by Git and must remain outside source control.

## 3. Creating Runtime ENV Files

From the project root:

```powershell
Copy-Item .\deploy\docker\.env.example .\deploy\docker\.env

Get-ChildItem .\deploy\docker\env\*.env.example | ForEach-Object {
    $Target = $_.FullName -replace '\.example$',''
    Copy-Item $_.FullName $Target
}
```

Then edit the new runtime files locally.

Do not replace unknown values in the checked-in templates with real production values.

Controlled placeholders:

- `<TBD>` - required value not yet supplied.
- `<TO_VERIFY>` - candidate value that still requires verification.
- `<NOT_APPLICABLE>` - intentionally not applicable only where the application accepts it.

## 4. Compose-Level Configuration

`deploy/docker/.env` is only for values Docker Compose needs before containers start.

Typical values include:

```text
COMPOSE_PROJECT_NAME
WEEKEND_REPORT_IMAGE
```

For a release deployment:

```text
WEEKEND_REPORT_IMAGE=weekend-report:<version>
```

The same application image is used by both the `web` and `worker` services.

## 5. Application Runtime Configuration

`deploy/docker/env/app.env` contains application-wide runtime settings, including:

- PostgreSQL database name/user/password;
- `WEEKEND_REPORT_DATABASE_URL`;
- application version/build ID;
- optional Git commit metadata;
- CSRF signing key and TTL;
- manual database synchronization review settings.

Production traceability requires real values for:

```text
WEEKEND_REPORT_APP_VERSION
WEEKEND_REPORT_BUILD_ID
```

The root `TAG` file remains the source version used by the release/image pipeline. Runtime
`WEEKEND_REPORT_APP_VERSION` should correspond to the deployed release.

## 6. Application Access, CSRF, and Reviewer Name

Weekend Report does not maintain application user accounts and does not require a login.

Application authentication, user-account, and session settings are not part of the runtime configuration.

Browser mutations are protected by:

```text
WEEKEND_REPORT_CSRF_SIGNING_KEY=<secret>
WEEKEND_REPORT_CSRF_TTL_SECONDS=3600
```

`WEEKEND_REPORT_CSRF_SIGNING_KEY` is required by production preflight and is generated by
`scripts/deployment/configure-app-env.ps1`.

The reviewer name is not configured in ENV. It is entered manually on the Review page during
final confirmation. The entered name is stored with the final decision and is rendered in the
Reviewer Confirmation section at the bottom of the final PDF.

## 7. Secrets and File Mounts

The base Compose file mounts:

```text
./secrets -> /app/secrets:ro
```

Typical deployment files may include SSH keys/known-hosts data required by enabled modules. No
Weekend Report user database is required.

Direct HTTPS additionally mounts:

```text
./tls -> /app/tls:ro
```

Never commit real secrets, private keys, tokens, passwords, or production `.env` files.

## 8. Sites and Infrastructure

Site identifiers and infrastructure inventory come from runtime ENV, not from `rules.yml`.

Infrastructure configuration includes:

- site display/identity values;
- SSH username;
- private key path;
- strict known-hosts path;
- expected Chrony source/timezone;
- numbered server lists per site.

Example container paths:

```text
SSH_PRIVATE_KEY_PATH=/app/secrets/ssh_private_key
SSH_KNOWN_HOSTS_PATH=/app/secrets/known_hosts
```

Server lists are dynamic. Increase the site server count and add the matching numbered variables
instead of modifying Python code.

Infrastructure policy remains in `rules.yml`, including filesystem and Chrony thresholds.

## 9. Portainer

Portainer runtime configuration contains only connection information.

It does not contain:

- a hardcoded expected service list;
- expected image references;
- image-comparison modes;
- hardcoded replica counts.

The application discovers Docker Swarm services dynamically from both sites.

For every discovered service it validates the actual site state, including desired/running replicas,
health when available, image traceability, and task/service state. Cross-site parity is then
evaluated separately.

Two sites being identically unhealthy must not produce a PASS.

Typical runtime fields include:

```text
PORTAINER_COLLECTION_MODE=live
PORTAINER_API_CONTRACT=docker_proxy_v1
PORTAINER_AUTH_TYPE=x_api_key

PORTAINER_SITE1_URL
PORTAINER_SITE1_ENDPOINT_ID
PORTAINER_SITE1_TOKEN
PORTAINER_SITE1_TLS_VERIFY

PORTAINER_SITE2_URL
PORTAINER_SITE2_ENDPOINT_ID
PORTAINER_SITE2_TOKEN
PORTAINER_SITE2_TLS_VERIFY
```

Portainer task-state and parity policy belongs in `rules.yml`.

## 10. RabbitMQ

RabbitMQ uses the Management HTTP API in read-only mode for both sites.

The collector performs only:

```text
GET /api/queues
GET /api/nodes
```

Runtime connection values are stored in `deploy/docker/env/rabbitmq.env`.

Typical configuration:

```text
RABBITMQ_COLLECTION_MODE=live

RABBITMQ_SITE1_URL=<TBD>
RABBITMQ_SITE1_USER=<TBD>
RABBITMQ_SITE1_PASSWORD=<TBD>
RABBITMQ_SITE1_TLS_VERIFY=true
RABBITMQ_SITE1_CA_FILE=

RABBITMQ_SITE2_URL=<TBD>
RABBITMQ_SITE2_USER=<TBD>
RABBITMQ_SITE2_PASSWORD=<TBD>
RABBITMQ_SITE2_TLS_VERIFY=true
RABBITMQ_SITE2_CA_FILE=
```

RabbitMQ Management URLs must use HTTPS in the production deployment helper.

### TLS verification

Two TLS modes are supported.

Use the container's normal trusted CA store:

```text
RABBITMQ_SITE1_TLS_VERIFY=true
RABBITMQ_SITE1_CA_FILE=
```

For an internal/private CA:

```text
RABBITMQ_SITE1_TLS_VERIFY=custom_ca
RABBITMQ_SITE1_CA_FILE=/app/secrets/rabbitmq-site1-ca.pem
```

The base Compose configuration already mounts:

```text
deploy/docker/secrets/ -> /app/secrets:ro
```

so custom RabbitMQ CA certificates belong under `deploy/docker/secrets/`.

`TLS_VERIFY=false` is not permitted for live RabbitMQ collection.

The deployment helper:

```text
scripts/deployment/configure-rabbitmq-env.ps1
```

can configure normal CA verification or copy a custom CA into `deploy/docker/secrets/` and write the corresponding container path to `rabbitmq.env`.

### Queue validation

All queues returned by `/api/queues` are inspected.

The required final values are:

```text
Ready   = 0
Unacked = 0
Total   = 0
```

Queue checking consists of one initial observation plus up to three refreshes when non-zero queue counts remain.

The current production policy in `rules.yml` is:

```text
refresh_attempts: 3
delay_seconds: 3
```

Therefore a persistently non-zero queue can be observed across four snapshots with three seconds between refreshes. If all queues are already zero, the collector does not perform unnecessary additional refreshes.

Queue counts that remain non-zero after all configured rechecks produce `ERROR`.

HTTP/API retry attempts are separate from queue-state refresh attempts.

### Node health validation

Every RabbitMQ node returned by `/api/nodes` must provide sufficient metrics to evaluate:

```text
File Descriptors
Socket Descriptors
Erlang Processes
Disk Space
```

The Weekend Report derives File Descriptor, Socket, and Erlang Process health from the Management API's used/total metrics using RabbitMQ Management UI thresholds.

File Descriptors:

```text
green   < 80%
yellow  >= 80%
red     >= 95%
```

Socket Descriptors:

```text
green   < 80%
yellow  >= 80%
red     >= 100%
```

Erlang Processes:

```text
green   < 50%
yellow  >= 50%
red     >= 75%
```

Disk Space uses `disk_free_alarm` when supplied by RabbitMQ. When that field is unavailable, the collector compares `disk_free` with `disk_free_limit`.

Weekend Report policy requires all four node indicators to be `green`. A yellow or red value is therefore unhealthy and produces `ERROR`.

If the Management API does not provide sufficient data to determine one of these resource states, Weekend Report does not fabricate a healthy result. It reports a technical `RABBITMQ_NODE_HEALTH_MAPPING_UNRESOLVED` error instead.

### Credentials

Use a dedicated RabbitMQ account intended for monitoring/read-only Management API access rather than an administrative account.

RabbitMQ credentials remain runtime secrets and must not be committed to source control.

## 11. DOCTOR

DOCTOR uses the live API contract and discovers each site's service inventory dynamically.

Runtime configuration:

```text
DOCTOR_MODE=api
DOCTOR_SITE1_API_URL=<TBD>
DOCTOR_SITE2_API_URL=<TBD>
```

There is no configured or hardcoded production service inventory.

For each site, the application obtains the current service state from the configured DOCTOR API.
The discovered service sets and health states are then validated and compared across the two sites.

Technical API, authentication, transport, and schema failures remain blocking errors.

Eligible service-health findings may enter the configured manual-review path. Manual review does not
rewrite the underlying health error to PASS, and cross-site parity cannot make two identically
unhealthy sites healthy.

The deployment scanner treats unresolved DOCTOR_SITE1_API_URL and
DOCTOR_SITE2_API_URL values as configuration that must be supplied before deployment.

## 12. Recording

Recording uses the existing-device workflow only.

Runtime ENV provides the Manager/WebApp endpoints and site server references. Safety, polling,
expected count deltas, cleanup, and recovery behavior remain in `rules.yml`.

Device creation/deletion is not part of this project.

Current implementation status:

```text
LIVE RECORDING COLLECTOR: INTENTIONALLY BLOCKED
```

The live control/read contract must be implemented and approved before the module can be enabled in
production.

## 13. Splunk

Splunk is a human dashboard-review workflow. Weekend Report does not automatically determine
dashboard health through a Splunk API.

Dashboard definitions come from numbered runtime ENV values.

Typical structure:

```text
SPLUNK_DASHBOARD_COUNT=<number>

SPLUNK_DASHBOARD_1_ID=<value>
SPLUNK_DASHBOARD_1_DISPLAY_NAME=<value>
SPLUNK_DASHBOARD_1_URL=<value>
SPLUNK_DASHBOARD_1_REQUIRED_REVIEW=true
SPLUNK_DASHBOARD_1_NOTE_REQUIRED=false
SPLUNK_DASHBOARD_1_ORDER=1
```

The dashboard count is dynamic. Add or remove numbered entries rather than changing application code.

`rules.yml` supplies the default dashboard-review policy:

```yaml
splunk:
  dashboard_defaults:
    required_review: true
    note_required: false
  open_all:
    include_optional: true
```

Each dashboard can override the default review behavior through its numbered runtime ENV entry:

```text
SPLUNK_DASHBOARD_N_REQUIRED_REVIEW
SPLUNK_DASHBOARD_N_NOTE_REQUIRED
SPLUNK_DASHBOARD_N_ORDER
```

The fields are independent:

* `REQUIRED_REVIEW=true` means the dashboard must be explicitly marked reviewed before APPROVE.
* `NOTE_REQUIRED=true` means a non-empty dashboard reviewer note is required before APPROVE.
* `ORDER` controls dashboard display order.

A dashboard may therefore be optional for explicit review while still requiring a note, or require
explicit review without requiring note text.

`OPEN ALL DASHBOARDS` follows `splunk.open_all.include_optional`. Required dashboards are always
included; optional dashboards are included when that policy is enabled.

The Splunk module's global reviewer-note requirement is separate from per-dashboard notes and remains
controlled by `rules.review.required_module_notes`.

The deployment helper:

```text
scripts/deployment/configure-splunk-env.ps1
```

creates the dynamic numbered dashboard inventory and prompts for review requirement, note requirement,
and display order for each dashboard.

## 14. Business Policy in rules.yml

`deploy/docker/config/rules.yml` is the single runtime policy file.

It controls stable, reviewable policy such as:

- module enablement and requiredness;
- unavailable/error behavior;
- aggregation;
- cross-site parity;
- Portainer task-state policy;
- RabbitMQ queue/node rules;
- infrastructure thresholds;
- Recording safety/recovery policy;
- review-note requirements;
- approve/reject readiness;
- stale-worker and recovery behavior.

Environment-specific addresses, credentials, server lists, dashboard URLs, and tokens do not belong
in `rules.yml`.

## 15. Deployment Helper Scripts

Optional helper scripts are stored under:

```text
scripts/deployment/
```

Current helpers:

```text
configure-app-env.ps1
configure-portainer-env.ps1
configure-rabbitmq-env.ps1
configure-infrastructure-env.ps1
configure-splunk-env.ps1
scan-unresolved-config.ps1
```

They resolve the project root relative to their own location and do not contain this development
PC's absolute path.

They are convenience tools, not runtime dependencies.

Important:

- create the real `.env` files from templates before running a configure helper;
- `configure-app-env.ps1` generates the PostgreSQL password/database URL and CSRF signing key;
- no application user/login configuration is required;
- `scan-unresolved-config.ps1` is useful on the deployment/build PC after the real ENV files exist.

## 16. Configuration Validation

From the project root, with all runtime ENV files created:

```powershell
python scripts/validate_config.py `
  --config deploy/docker/config `
  --env-file deploy/docker/env/app.env `
  --env-file deploy/docker/env/portainer.env `
  --env-file deploy/docker/env/doctor.env `
  --env-file deploy/docker/env/rabbitmq.env `
  --env-file deploy/docker/env/recording.env `
  --env-file deploy/docker/env/infrastructure.env `
  --env-file deploy/docker/env/splunk.env
```

For non-production shape/schema validation:

```powershell
python scripts/validate_config.py `
  --config deploy/docker/config `
  --no-production-preflight
```

The deployment helper scan can also be run after real ENV files exist:

```powershell
.\scripts\deployment\scan-unresolved-config.ps1
```

A production deployment is not ready merely because ENV syntax is valid. Live-module implementation
blockers described above must also be resolved or explicitly disabled according to approved
`rules.yml` policy.
